## ✅ Travail effectué

Journée dominée par une **découverte critique** : l'application était **hors service en production**, et la cause n'était pas celle qu'on croyait. Le projet Supabase utilisé par le backend s'était **mis en pause tout seul** (plan gratuit, inactivité), et Supabase retire le DNS des projets en pause — le nom de domaine de la base ne répondait donc plus du tout. C'est l'explication exacte du « fetch failed » remonté par Patrick, qu'on attribuait jusqu'ici à une vieille version de l'APK. Dans la foulée : **bascule complète vers le Supabase du client**, application de **8 migrations de sécurité** fermant **9 failles** toutes exploitables avec la clé publique embarquée dans l'APK, **durcissement du stockage** (6 buckets sans aucune restriction de type de fichier), et **démarrage de la migration Supabase-only** avec un premier module porté et vérifié identique à l'octet près. Tout validé par typecheck (**0 erreur**), 65 tests au vert, et surtout **vérifié en conditions réelles** sur la base de données live — pas seulement affirmé.

### 🔴 Panne de production — cause trouvée après une fausse piste

- L'API répondait `200` sur `/api/health`, ce qui donnait l'illusion que tout allait bien. En réalité **aucune requête touchant aux données ne fonctionnait**.
- **Fausse piste assumée** : un test de connexion renvoyait un `401` propre en 0,45 s, ce que j'ai d'abord interprété comme « la base répond ». C'était faux — le code transforme **toute** erreur d'authentification en `401 identifiants invalides`, donc une base morte et un mauvais mot de passe sont indistinguables de l'extérieur. Et c'était rapide _parce que_ le DNS échouait instantanément.
- Confirmé sans ambiguïté ensuite : `nslookup` → domaine inexistant, statut projet → `INACTIVE`. Le backend appelait une base qui n'existait plus.
- **Leçon appliquée** : la nouvelle fonction de health interroge réellement Postgres. Un contrôle de santé qui ne touche pas ses dépendances affiche « en ligne » pendant que la base derrière a disparu — exactement ce qui a masqué la panne.

### 🔐 Sécurité — 9 failles fermées, toutes vérifiées en réel

Toutes étaient atteignables avec la clé publique qui est **dans l'APK** (extractible en quelques minutes).

| Faille                           | Impact avant correction                                                     |
| -------------------------------- | --------------------------------------------------------------------------- |
| Élévation de privilèges          | N'importe qui pouvait se passer `admin` sur son propre compte               |
| Inscription admin                | S'inscrire avec `role: admin` créait un administrateur                      |
| Fuite de données                 | Emails, téléphones et identifiants Stripe de tous les utilisateurs lisibles |
| Contournement du paywall         | Drafts illimités en écrivant directement en base                            |
| Falsification de messages        | Envoyer un message **au nom de l'autre personne** d'une conversation        |
| Manipulation du classement       | Un athlète pouvait fixer lui-même ses compteurs de vues/likes               |
| Contournement du contrôle mineur | Un athlète pouvait modifier sa propre date de naissance                     |
| Badge « vérifié »                | Un recruteur pouvait se déclarer vérifié lui-même                           |
| 2 IDOR                           | Données privées de profil et de classement exposées par identifiant         |

- **Fuite de revenus corrigée** : le quota gratuit de Drafts se réinitialisait **tous les jours au lieu de tous les mois** — l'offre gratuite était environ **30× plus généreuse** que prévu. Deux composants faisaient chacun leur propre réinitialisation ; il n'y en a plus qu'un seul. Vérifié en prod : `swipesRemaining: 20` par mois.
- **Course sur les paiements corrigée** : deux achats de pack de Drafts simultanés s'écrasaient mutuellement, faisant **disparaître des Drafts déjà payés**. Remplacé par un compare-and-swap, avec journalisation explicite si le crédit échoue malgré tout.
- **Bug trouvé pendant la revue, absent de l'audit** : après avoir déplacé le rôle dans la zone protégée, un utilisateur qui changeait de rôle pendant l'inscription restait **bloqué à vie sur son rôle initial** — la valeur périmée gagnait sur la colonne corrigée. Un recruteur se serait retrouvé en 403 sur sa propre partie de l'app.
- **Tests en trompe-l'œil découverts** : la suite passait au vert sans rien prouver (le mock ne contenait pas la fonction appelée, l'erreur était avalée silencieusement). Ajout de 12 tests qui vérifient réellement la propriété de sécurité — et **validés par mutation** : en réintroduisant volontairement la faille, 2 tests échouent bien.

### 🔄 Bascule vers le Supabase du client

- **8 migrations appliquées** (031→038) sur le projet du client, chacune vérifiée après coup en interrogeant la base live.
- Backend repointé, redéployé, et **testé de bout en bout** : création de compte (rôle `coach` correctement conservé, pas dégradé en `athlete`), connexion, Discover, profil, abonnements, classements, posts, messages, matchs, KYC — **tous en 200**.
- **Email de production configuré** : le projet utilisait l'expéditeur de test partagé de Supabase, plafonné à **2 emails/heure** — c'est ce qui bloquait toute inscription. Basculé sur Resend.
- **Bug trouvé** : `app.json` pointait toujours vers l'**ancien projet supprimé**. Seul le parcours OAuth le lit, donc rien ne l'avait révélé — mais il aurait échoué dès l'activation d'un fournisseur.
- **Piège d'ordonnancement documenté** (et je m'étais trompé de sens au premier passage) : il faut déployer le backend **avant** les migrations. L'inverse aurait transformé chaque inscription coach/recruteur/parent en athlète.

### 🗄️ Stockage — audit inédit

- Personne n'avait jamais regardé la configuration des buckets. Résultat : **les 6 acceptaient n'importe quel type de fichier**, et **5 étaient publics**.
- Un bucket public sert les fichiers à quiconque a l'URL : pas d'authentification, pas d'expiration, pas de révocation. Combiné à « tout type de fichier », c'est un hébergeur de fichiers ouvert sur le domaine du projet.
- `guardian-videos` (enregistrements de consentement parental de mineurs) était correctement privé mais **sans aucune limite de taille**.
- Corrigé : listes blanches de types MIME sur les 6 buckets (SVG exclu partout — image pour un chef de produit, conteneur de script pour un navigateur), plafonds de taille partout.

### ⚙️ Migration Supabase-only — fondations posées

- Objectif : supprimer le serveur backend séparé. Programme long (17 modules restants), mais l'approche est maintenant **prouvée**.
- Couche partagée construite et déployée, reproduisant **exactement** le format de réponse actuel — c'est le pari central : les 17 modules côté client gardent leurs 99 signatures, seul le contenu change.
- **Premier module porté** (classements) et comparé requête par requête à l'API existante : **identique à l'octet près** sur les 5 cas testés, y compris le message d'erreur de validation d'UUID.
- **Limite honnête consignée** : la base est vide, donc la parité est prouvée sur des résultats vides. À revérifier avec de vraies données avant de basculer le client.

### 🆓 Rendre le plan gratuit viable jusqu'au passage payant

- **Mise en veille** → résolu : une tâche planifiée interroge la fonction de health toutes les 10 minutes, ce qui compte comme activité. Elle vérifie `db:"up"` et pas seulement le code HTTP.
- **Sauvegardes** → partiellement résolu : le plan gratuit n'en a **aucune**. Tâche nocturne écrite (dump compressé, conservé 30 jours, en artefact et non dans le dépôt — un dump contient les données personnelles de tous les utilisateurs et l'historique Git est éternel).
- **Stockage 1 Go** → **non résolu, seulement repoussé**. Les plafonds d'origine (50 Mo par vidéo) remplissaient le projet en ~20 clips. Rebudgété à 15 Mo → environ **65 vidéos au total, tous utilisateurs confondus, pour toujours**. Suffisant pour les tests internes, **insuffisant pour un lancement public** — aucun réglage ne fait tenir un produit vidéo dans 1 Go.
